Do PCAP features help on our three datasets?

A guide for checking whether packet features extracted from the PCAP/PCAPng files and attached to the CICFlowMeter v4 CSV improve detection on ASEADOS-SDN-IoT, CyberFlowIoT-GICAP and TII-SSRC-23. It extends Thesis 2 – RESEARCH.pdf (Q3: what new features can we add).

Study design: the raw PCAP/PCAPng files of the three datasets in 01_raw_datasets → CICFlowMeter v4 CSV → PCAP-derived columns attached with pcap_flow_enricher.py. The Thesis 1 data (TRUSTLab, CSE-CIC-IDS2018) and the CSVs published with each dataset are not used as model input. Every added column is computed directly from the packets in the PCAP/PCAPng with Scapy; no NetFlow, nProbe or NFStream exporter is used.

Short answer

They should help on specific attack classes, not on every class, and only an ablation test can prove it. The gain depends on what CICFlowMeter v4 misses in each dataset. Where the attack lives in traffic that v4 drops or summarises away (ARP, DNS content, payload, packet order, activity across flows), the added columns carry new information. Where v4's flag counts and rates already separate the classes, expect little or no gain.

Every claim below is tagged with the kind of basis behind it:

Measured from our own runs on the samples Literature reported in a cited study Hypothesis to be tested by the ablation Risk could make a gain fake

Expected gain per dataset

Expected gain: high CyberFlowIoT-GICAP

Several classes live where v4 is blind: ARP spoofing (non-IP), DNS beaconing (DNS fields and timing), SQL and MQTT injection (payload content), Nmap (many ports across flows).

Expected gain: medium ASEADOS-SDN-IoT

Slow DoS vs HULK and probe vs DDoS can use TCP window, packet order and window counts. But 45% of the sample's IP packets are IPv6, which v4 ignores, and labels are per capture file.

Expected gain: low to medium TII-SSRC-23

Most of its 12 DoS subtypes are defined by one TCP flag, which v4 already counts. Gains are likely only for ECN DoS, MAC DoS, brute-force subtypes and Mirai variants.

Class-by-class assessment

For each attack class in the datasets: which PCAP-derived columns should contribute, and the basis. "None expected" means v4's existing columns already describe the attack.

Where the columns come from: every column in the "PCAP columns" tables is computed by pcap_flow_enricher.py from the packets in the raw PCAP/PCAPng (TTL, TCP window and options, DNS, ICMP, payload bytes, packet order, ARP). The only exception is marked †: the window columns (win2s_*, win60s_*) are computed from the v4 CSV's Src IP, Dst Port and Timestamp, which CICFlowMeter itself took from the same PCAP. None of these columns exist in the CICFlowMeter v4 output.

Risks that can produce a fake gain, and the solution for each

A "gain" only counts if it survives these checks. Each solution is a concrete step you can put in the methodology chapter.

Final conclusion to use

Use the CICFlowMeter v4 baseline plus a small set of PCAP-derived feature groups, each tied to an attack class that v4 cannot describe, and keep a group only if the capture-grouped ablation shows a real gain.

  • Input data: the raw PCAP/PCAPng of ASEADOS-SDN-IoT, CyberFlowIoT-GICAP and TII-SSRC-23, converted with CICFlowMeter v4. No published CSV and no Thesis 1 dataset is used.
  • Baseline: the 76 v4 statistical features, identical across the three datasets because all go through the same extractor.
  • Added: the PCAP-derived columns from pcap_flow_enricher.py, computed from the packets of the same raw files and attached to each v4 flow row.
  • Priority groups: (1) window aggregates for scans, floods, brute force and beaconing, now possible on all three datasets; (2) ARP features for CyberFlow's ARP spoofing, which v4 cannot see at all; (3) DNS features for DNS beaconing and DNS brute force; (4) TCP window and first-10 packet sizes for slow DoS vs HULK; (5) payload statistics for SQL/MQTT injection, plaintext only.
  • Test only, not assumed: TTL (possible artifact), ECN, ICMP and retransmission counts.

Why this gives better anomaly detection: CICFlowMeter v4 describes each flow in isolation and only by size, timing and flag summaries. Attacks that live in what it throws away (ARP, DNS content, payload, packet order, behaviour across flows) are where detectors fail, and those are exactly the gaps these groups fill. The measured gaps (dropped ARP and IPv6, 1,000 ports per source in the Nmap sample) show the information is missing; the literature (Sarhan et al., Kitsune, Luay et al., payload studies) shows such fields carry attack signal; and the capture-grouped ablation with repeated runs makes sure any improvement is real rather than leakage. If a group does not help on a dataset, that is reported as a finding, which strengthens the thesis instead of weakening it.

Plan for selecting the necessary features

A feature is "necessary" only if it passes every stage below. Stages 2–4 run inside the training folds only, so the selection itself never sees test data.

  1. Candidate pool. 76 v4 statistical features + 45 PCAP-derived columns (8 groups). Every candidate has a reason in the class tables above.
  2. Quality filter. Drop identifiers (Flow ID, IPs, Src Port, Timestamp), columns with near-zero variance, and one of each pair with correlation > 0.9 (keep the one with higher importance). Basis: Yasarathna & Le-Khac 2026; Awad et al. 2022.
  3. Artifact screen. For TTL, TCP window, inter-arrival time and Dst Port, check per class whether one value identifies a class by itself. If so, mark the column "artifact risk" and evaluate with and without it. Basis: Cerasuolo et al. 2026; Sarhan et al. (arXiv 2108.12732).
  4. Relevance ranking. Permutation Feature Importance, repeated (e.g. 10 runs) with two models (XGBoost, Random Forest), plus Mutual Information as a model-free check. Keep columns whose mean importance is ≥ the mean of all columns in at least one dataset. Basis: Herzalla et al. 2023 (PFI); Nouman et al. 2026 (MI); Awad et al. 2022 (mean threshold).
  5. Group ablation. Baseline 76 → + each PCAP group → + all surviving groups, with capture-grouped folds and fixed hyperparameters. A group stays only if macro-F1 or its target class F1 rises by more than the fold-to-fold spread. Basis: risk table above; Arp et al. 2022.
  6. Cross-dataset check. Train on two datasets, test on the third, with family-level labels (benign, DoS/DDoS, scan/probe, brute force, botnet, MITM/ARP, injection). A group that helps in-dataset but hurts transfer is reported, not silently kept. Basis: Bilal et al. 2025; Cerasuolo et al. 2026; Rodríguez et al. 2026.
  7. Final set and explanation. Final features = baseline columns that passed stages 2–4 + PCAP groups that passed stage 5. Explain the final model with SHAP and list, per class, which PCAP columns it relies on.

How to test whether the features really help

  1. One extractor. Generate a CICFlowMeter v4 CSV for every raw PCAP in 01_raw_datasets (CyberFlow: the .pcap copies in 02_Pcap; TII: extract each zip first). The published CSVs are not used.
  2. Enrich. Run pcap_flow_enricher.py on each PCAP + CSV pair. Accept a file only if packets per flow match CICFlowMeter's own count (samples: TII 100%, CyberFlow 99.9%).
  3. Label and clean. Label each flow from its capture's folder (ASEADOS: bot, ddos, dos/hulk|slow|torsh, prob, benign; TII: the attack subtype in the file name; CyberFlow: the attack type and time window in Pcap_Attack_Map.csv), then refine by attacker IP and time window. Drop identifiers after computing window features.
  4. Split by capture file (grouped cross-validation), or by time where a class has one capture; the same folds for every run.
  5. Baseline: XGBoost on the 76 v4 statistical features, fixed hyperparameters. (The Thesis 1 set of 66 removed 12 columns only because of TRUSTLab, which is not used.)
  6. Ablation: baseline + all 45 columns; then baseline + each group alone (IP header, TCP, ICMP, DNS, payload, packet order, ARP, window); then all without TTL.
  7. Repeat each run with 5 seeds or 5 capture-based folds, and report mean ± standard deviation.
  8. Judge "it helps" only when macro-F1 or a target class's F1 rises by more than the spread across seeds, and SHAP shows the new columns among the ones the model actually uses.
  9. Report per dataset and per class, including the classes where nothing changed. A null result on TII's flag DoS is an expected and useful finding.
